Every map of build 24919, read offline from the install (T035, T045). This page covers the catalogue (§1); the
complete map-data format: header, environment, all record types, instance data, collision, AI and sound data (§2);
which placements the server must create (§3); spawn rooms (§4); choosing a map (§5); what is script-driven or
server-only (§6); what a map pulls in (§7); the load sequence (§8); tools, meaning our parser/writer and the
explorer's map view (§9); and editing a map (§10).

[LobbyServer.md](LobbyServer.md) "Practice vs AI and Private Game" (the custom-game messages),

## 1. The catalogue

Generated by `systems/data/maps/tools/mapgen` (Go, cgo over `systems/content` + `systems/stu`):

```
cmake --build systems/content/build && cmake --build systems/stu/build   # the static C APIs
cd systems/data/maps/tools/mapgen && go run .                           # ~10 s
```
writes `systems/data/maps/maps.json` (everything below, per map) and `server/internal/maps/maps_gen.go`
(the tables the servers use; package `maps`: `All`, `ByData`, `Find`, `Playable`, `PlayableData`,
`Map.StartSpawns`). Names come from `systems/data/lobby_scripts/strings_enUS.tsv`.

## 2. The map data (resource type 0x002, "MAPDATA")  [D, G]  (T035, format completed in T045)

One blob per map, 2.6–119 MB, read by our parser `systems/maps` (§9). **Every byte range is accounted for**:
on all 19 maps, every section is walked by record sizes and ends exactly at its size, and every instance-data
blob, both AI blobs and every collision pointer lands inside the file. "Consumer" names the client
function that reads a field; where only the data was read, the tag is [D].

### 2.1 Layout (Anubis, 45,996,848 bytes)

| range | what | consumer |
|---|---|---|
| `+0x000…+0x31F` | header (§2.2) | world creation / static world / load loop |
| `+0x320…+0x83A8F` | 14 record sections (§2.3, §2.4), not in type order (1, 2, 8, 9, 11, [blobs], 13, 3, 10, 4, 14) | §2.4 |
| `+0x5F5A0…+0x7798F` | 976 instance-data STUD blobs of the entity records (§2.5), between sections 11 and 13 | MAPDATA constructor |
| `+0x83A90…+0x1FAD76F` | static collision triangle mesh: vertices, triangles, BVH (§2.6) | physics world |
| `+0x1FAD770…+0x1FBFA87` | collision shape tables: capsules, convex hulls (+ their data), the mesh item | physics world |
| `+0x1FBFA88…+0x2BC2DC7` | AI navigation (STUD, 12 MB) | `FUN_7ff6509da200` |
| `+0x2BC2DC8…+0x2BDD917` | AI tactical volumes (STUD, 110 KB) | same |
| `+0x2BDD918…` end | sound-volume → sound-space table (22 × 24 bytes) | sound system [?] |

**The MAPDATA handler** (resource handler slot 18; type → handler table at RVA `0x146c5f0`) [G]:
Construct `FUN_7ff6509b78a0` → `FUN_7ff650ef9130`: turns the header's seven 64-bit offsets (`+0x2D8…+0x2F8`,
`+0x300`, `+0x310`) and the pointers inside the hull (4) and mesh (3) items into absolute pointers
(`FUN_7ff650ef9270`), then loads **every entity's instance-data blobs and the two AI blobs in place** as STU
documents (`FUN_7ff650813ce0`). So the blob is used as it sits in memory, and nothing is copied.

### 2.3 Records

Every record starts with a 0x18-byte header [G]:
```
+0x00 UUID[16]   placement GUID (the spawned entity's +0x18; zero on model groups, whose instances carry their own)
+0x10 u8 flags   bit0 gameplay, bit1 presentation (model-only), bit3 "large": drawn in the far LOD class
                 (static world: iVar26 = 3), types 1/2/8 only
+0x11 u8         0 on every record
+0x12 u8 pass    load pass (0 everywhere)
+0x13 u8 type    = the section's type
+0x14 u32 size   the next record follows
```
**Two consumers split the types** [G]:
- **Types 1–7, the static world** (`FUN_7ff650a04e60`, called from `FUN_7ff650a065d0` at map start): no entities
  are created. Model groups, models and map text become render instances; occluders, reflection probes
  and text labels go into lists. Types 3, 4 and 6 are skipped on a null renderer (render device vfunc 0x50).
- **Types 8–15, the placed entries** (the load loop `FUN_7ff650a233f0`): one 0x38-byte entry each, in type
  order. That is the **placed index** a server's from-map create sends. An entry is started through
  MapWorldSystem's hook for entities, and through the default per-type start `FUN_7ff650a285d0` otherwise.

In the whole install there are 31,970 records of 14 types. **Types 0 and 5 never occur**: type 5 is counted in the load
progress (`FUN_7ff650a065d0` adds count[5]), but no reader for it was found.

### 2.5 Entity records (type 11) and their instance data

```
+0x18 u64 definition (003)       +0x20 pos  +0x2C scale  +0x38 rot (x,y,z,w)
+0x48 u32 n (instance-data pairs)
+0x4C…+0x57 mostly 0 (half floats when set; +0x52 u16 / +0x54 go to the model component, FUN_7ff6509c1820)
+0x68 u32 != 0 → scene flag 0x10000 (43 records)
+0x70 u64 skin: STUSkin (076), bits 32–47 = variant 1–8, bit 31 = a flag (60 records)
+0x78 u32 (1 on 1,406 records)
+0x80 n × {u32 slot, u32 offset}: the blob starts at pair + offset
size = 0x80 + 8n (holds for all 14,137)
```
The spawn (`FUN_7ff650a293d0`) resolves the definition, copies the UUID to the new entity, and gives each component
its override: for every definition component, `DAT_7ff651834a00[runtime id]` is compared with the pair's slot,
and the loader gets `blob + 0x10` (the loaded STU instance) for that component [G]. 15,773 blobs in the install, and
**all of them parse with the client registry, every layout CRC matching** [D, `install_all_maps_parse`]:
`STUECSpawnInstanceData`, `STUStatescriptComponentInstanceData`, `STUTargetTagInstanceData`, …

**Placed index**: the record's position among the records of type ≥ 8 in type order. On Anubis, types 8/9/10 hold
80 + 57 + 37 = 174 records, so entity record `k` has placed index `174 + k`. This was checked against every index
known live (the ship door `0x1d7`, doors `0x1d8…0x1dc`, spawns `0x1dd…0x1f0`, …) [L]. The entry classifier
`FUN_7ff650a28720` switches on these types [G].

### 2.6 Static collision  [G, D]

The physics world (`FUN_7ff650a239a0`, only when world flag 0x200 created one) adds four shape kinds to its scene
(`FUN_7ff651193ee0`, kind 0–3). The material block (friction, restitution, …) is the same in every item:
| kind | table / item size | content |
|---|---|---|
| 0 sphere | `+0x2D8`, 0x60 | `+0` u64 −1, `+0x08` centre, `+0x14` radius, `+0x20` friction, `+0x50` u16 mask, `+0x52` material + flags, `+0x5D` u8 pass-through |
| 1 capsule | `+0x2E0`, 0x68 | `+0x08` p0, `+0x14` p1, `+0x20` radius, `+0x2C` friction, `+0x50` mask, `+0x52` material + flags, `+0x5C` pass-through |
| 2 convex hull | `+0x2E8`, 0x90 | 4 pointers (below), `+0x20` centre, `+0x2C` V, `+0x30` F, `+0x34` half-edges (V − E/2 + F = 2 holds: 44, 24, 132), `+0x50` friction, `+0x78` mask, `+0x7A` material + flags, `+0x84` pass-through |
| 3 triangle mesh | `+0x2F0`, 0x58 | `+0x00` **BVH nodes** (32 bytes), `+0x08` vertices (vec4), `+0x10` **triangles** (32 bytes), `+0x18` node count, `+0x1C` vertex count, `+0x20` triangle count, `+0x24` BVH depth, `+0x28` u32, `+0x40` mask, `+0x52` pass-through (corrected in T062, see below) |

Item filter [G, `FUN_7ff650a239a0`; T066]: each item's fixture gets category 0x0001, or 0x0800 when its pass-through byte
is set, and the item's mask; the mesh item's mask is 0xFFFF on every map (its triangles carry their own). [D] No item of
the 19 maps has the pass-through byte set.

**Convex hull arrays** (T066, [D]: every one of the 1,978 hulls of the 19 maps checks out, `systems/maps`
`install_collision_hulls`): `+0x00` vertices, packed vec3 (12 bytes); `+0x08` face planes {normal, d} with n·x = d,
outward (every vertex of a face lies on its plane within 0.01); `+0x10` half-edges, 4 bytes {s8 twin delta (+1 / −1: twins
are adjacent), u8 origin vertex, u8 face, u8 next}; `+0x18` u8 first half-edge of each face. In the file they sit in the
order first-edges, half-edges, planes, vertices, just before the item table.

Every map has **exactly one** triangle mesh: it is the level geometry's collision, e.g. Anubis 522,648 triangles, 349,549
BVH nodes and 297,924 vertices (the 32 MB after the record sections), Dorado 891,931 triangles. Capsules, hulls and spheres are
the extra shapes (Anubis 118 capsules and 59 hulls; Hanamura 130 spheres). **Consequence for edits**: moving a
placement moves its entity, not this baked collision (§10).

**Mesh records and what the physics world does with them** (T062, [G]; docs/Movement.md §4):
- The mesh's first and third pointers were swapped here and in `systems/maps` (`CollisionMesh`: `tris` / `bvh`; fixed in
  T066, with tests that walk every map's BVH):
  `FUN_7ff6511adca0` copies +0x00 / +0x08 / +0x10 to the shape's nodes / vertices / triangles, the BVH walk
  (`FUN_7ff6511ae280`) walks +0x00 as nodes, the closest-point loop iterates +0x20 records of +0x10 as triangles.
  (Anubis: 522,648 triangles ≈ 1.75 × vertices, 349,549 nodes ≈ 1.5 triangles per node.) Earlier counts on this page
  that quote "triangles" for +0x18 are node counts.
- **BVH node** (32 B): min xyz, max xyz (f32), +0x18 i32 (internal: the right child is **this node + the offset**, left =
  next node; leaf: first triangle), +0x1c u16 mask (OR of its triangles' masks), +0x1e u8 (0 / 1 / 2 on internal nodes =
  the split axis, 3 on leaves; the layout of Box3D's `b3MeshNode`, Physics.md §5.2), +0x1f u8 triangle count (0 = internal). Root = node 0, pre-order. A query visits a node
  only if `mask & the querying fixture's category`. [D, T066] On all 19 maps the walk from the root reaches every node
  once, the leaves cover every triangle exactly once, every box contains its triangles, every internal mask is the OR
  of its children's, and the deepest leaf is at the depth `+0x24` (Anubis 522,648 triangles, 349,549 nodes, 297,924
  vertices, depth 32).
- **Triangle** (32 B): +0x00/+0x04/+0x08 i32 vertex indices, +0x0c/+0x10/+0x14 i32 **wing vertices** (the opposite
  vertex of the triangle across edge v0v1 / v1v2 / v2v0, −1 = open edge; used to reject internal-edge contacts),
  +0x18 u16 material, +0x1a u16 surface flags (bit 0 needed for the ground probe [? walkable]), +0x1c u16 mask.
- The physics world is Blizzard's own `dm` library; `FUN_7ff650a239a0` creates one static body and a fixture per
  item (`FUN_7ff651193ee0`): category 0x0001 (0x0800 when the item's flag byte is set: characters pass through
  those), the item's mask, restitution 0, infinite push limit; the mesh with friction 0.9. Characters collide with the
  mesh through a capsule (Movement.md §4.3–§4.5).

**What the masks say** (T066, [D] over the 19 maps; the meaning of categories other than the heroes' is not known):
heroes are categories 0x08 / 0x10 (Movement.md §4.3), so only triangles whose mask has one of them block heroes. Most
don't: on Anubis 345,703 of 522,648 triangles have masks like 0x0440 / 0x0040 (no hero bit), 173,665 block heroes and
others (0xFFFF, 0xFBBF, 0x1B9F, …), and 3,280 have masks inside 0x001A (heroes only). Most of the latter's area is 150
closed boxes (the 1,800 triangles of mask 0x001A, material 1, flags 0x2 / 0x3; 78,961 m², the largest area of any
mask/material group) reaching up to y 40: invisible walls and roof blockers [inferred: "player clip"]. The other maps are
similar (Dorado: 146,979 / 13,731 / 1,173,613). Anubis' 118 capsules all have mask 0x0440 (no hero bit); its hulls mostly
block heroes. Placements sit on this mesh: 20 of Anubis' 22 networked entities (the spawn points) are 0.0–0.1 m above a
hero-blocking floor straight below them (explorer `internal/mapview` `TestGeometry`), so the map records and the
collision share one coordinate frame. The explorer's 3D map mode draws all of it (docs/Explorer.md "3D map mode").

## 3. Which placements the server creates

- **Networked** = entity placements whose definition has **`STUSpawnComponent`** (`0xe880f3c4`, runtime 0x2e) or
  **`0x86ed8f46`** (runtime 0x73 SpawnPointInfo) [D]: the spawn points (def `0x167`) and the target-tag entities
  (`0x176`, `0x7a4`). This reproduces the client's list on Anubis exactly: **generated == the hand list**
  (`0x1dd…0x1f0, 0x41d, 0x41e`; test `TestAnubisNetworkedEqualsHandList`) [L].
- On Hanamura (22) and Gibraltar (40) `/setup` created the generated list, the local player finished (the hero
  lock-in ran) [L], and the client's side looks exactly as on Anubis: one server entity (`0x4000xxxx`, with the
  network components 0x0e/0x10/0x7a) **and** one local copy (`0x8000xxxx`, components 0x01 0x03 0x23 0x2e 0x68
  0x73) at every networked placement, no more, no fewer [L]. (Local copies of earlier maps stay in the game EA
  after a map change: this client process still held Anubis' and Gibraltar's while on Hanamura.)
- **Why both exist** (T037, [MatchLogic.md](MatchLogic.md) §8.2) [G, L]: the client's load loop spawns every
  gameplay placement locally, without looking at the network; the from-map create spawns a second entity and
  rebinds the placed entry (+0x28) to it, and nothing deletes the local copy. No record flag marks a placement as
  server-owned: record `+0x10` is `0x01` gameplay / `0x02` model-only prop / `0x03` both, uniform per definition
  (`systems/data/maps/tools/recflags`). The client's "networked" list only gates the local-player init. Creates
  must come after the load: a from-map create before the loader has visited the entry reads a null record.
- **Movers** = entity placements with a movement state: `STUMovementStateComponent` or a component that pulls
  0x12 in (`STUMirroredAnimComponent` 0x1c, `0x1b54380e` 0x2a) [D]. Anubis' 7 equal MatchLogic.md §8.1
  (indexes, positions, yaws; test `TestAnubisMovers`) [L]. Not created by `/setup` yet (T008).

The game server's `setupWorld` sends one from-map create per networked placement of the connection's map
(`maps.ByData(c.Map).Networked`), entity ids 3, 4, … (≤ 43 on any map; the ids are 8-bit).

## 4. Spawn rooms  [D, ? for the meaning]

Every spawn point carries `STUECSpawnInstanceData` {`0xcccec698` []team enum, `m_spawnPriority`, `0x2b91afbe`}
and a Statescript override for its graph `0x0D6`: ConfigVars `0x0D8…2B9` and `0x0D8…2BA` (default 0 in the
graph, which compares them with the var `0x0D8…806`) [D]. Grouping points with equal (team, priority, flag, 2B9,
2BA) gives **rooms of exactly 6 points** on every playable map (3–6 rooms per map).

Reading them against the map layout [?]:
- **team 1 = attackers, team 0 = defenders**: team 1's from-0 room is behind the first objective on every map
  (Anubis: next to the attackers' ship door, `0x1e3…0x1e8` at z ≈ −44; Gibraltar: the payload start).
- **2B9 = `From`, 2BA = `Until`**: the objective progress range a room is used in (Until 0 = to the end);
  `0x0D8…806` is presumably the objective progress. Anubis attackers move up after point A (From 1, priority
  2); Gibraltar switches both teams' rooms at 2 and 4 (its checkpoints); higher priority wins when two rooms of
  a team are active.

| map | rooms (team: from–until, priority) |
|---|---|
| Anubis | def 0–, att 0–, att 1– (p2) |
| Gibraltar | att 0–2, att 2–4, att 4–; def 0–2, def 2–4, def 4– |
| (all) | `systems/data/maps/maps.json` `spawns[]`: index, team, priority, flag, from, until, room, pos, yaw |

**Spawn-room volumes** [D]: next to every room sit 6 local entities of def `0x29f` (Statescript + empty target
tags) running graph `0x1ce`: `SetTeamIndex(owner, $03F8)` with `$03F8` an **`STUConfigVarTeam`** from the placement's
instance data (`0xf26a2fc7` = team, same numbers as the spawn points: Anubis 1 at the attacker start, 0 in the
defender room), and target tag `0x0D6…35` added / removed when the progress var `$0806` equals 2B9 / 2BA, set by
game message `0x0240000000000071` (param `0x0a4…55`); `$06EE` = the room is active at the start. So `$0806` **is** the
objective progress, the server sends it with game message `0x…71`, and the rooms' teams agree with the spawn
points' [D]. Its `SetTeamIndex` / target-tag actions are server-only (§6).

**Player team**: controller and hero get team 1 (filter bits, [MatchLogic.md](MatchLogic.md) §11), spawn points their
own team.

**The hero spawns at the attackers' start room** (`maps.Map.StartSpawns(TeamAttack)`, n-th hero body → n-th
point): the hero create carries the point's position/rotation **and a movement snapshot** (`Mover{Pos, Yaw}`, flag
0x02): without the snapshot the body's movement state put it back near the origin (−0.99, 1.3, 0.97) [L]; with it
Genji stands at (−13.87, −0.07, −161.22), Gibraltar's first attacker point, and stays there [L].

## 10. Editing a map  (T045)

What a map edit needs, and what exists now:
1. **A map data writer** (`systems/maps`, done):
   - In-place edits: move, rotate or scale any record with a transform, and change an entity's definition.
   - `AddEntity`: inserts a copy of an entity placement at the end of the entity section with a new placement
     GUID, a transform and its own copies of the instance-data blobs (a blob is loaded in place, so it can't be
     shared). Everything after the insertion point moves by 16-aligned deltas, and the writer rewrites the header
     offsets, the collision tables and the pointers inside hull and mesh items, the AI and sound-table offsets,
     and every entity's pair offsets. Tested on Anubis: the result parses, and every record, blob, the nav blob
     and the collision vertices are byte-identical at their new positions.
   - What an add changes for a server: placed indexes of types 12–15 shift by one; entity indexes (the from-map
     creates) do not.
   - Not in the writer: removing records, and adding records of other types (the same relocation would do). The
     baked collision mesh and the AI navigation are not updated, so a moved prop keeps its old collision unless
     its definition carries its own physics.
2. **An STU writer for headers**: only needed to change `STUMapHeader` fields (name, previews) or to add a
   map. Moving and adding placements doesn't need one. `systems/stu` has no writer yet (UISystem.md §5 route a).
3. **Delivery**:
   - Offline CASC patching (encoding table, index, APM package record + CKey) is heavy.
   - **Runtime injection** is cheap. The Prometheus MCP tool **`inject_resource {guid, path}`** (T045; the injector
     UISystem.md §4 asked for) reads a file and calls the engine's create-from-memory (`FUN_7ff6509a5de0` →
     `FUN_7ff6509a9130`). The resource entry is created (or found) and gets the buffer; the normal MAPDATA
     construct runs, and the handle is kept so the resource stays resident. When 20600 later names that map,
