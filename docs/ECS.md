# ECS (Entity / Component / System)

Reverse-engineered behaviour of the Overwatch beta 0.8 (build 24919) client ECS.
Reference for the clean-room reimplementation in `systems/ecs/` (see `systems/README.md`).

Per-component and per-system catalogue: [ECS_Components.md](ECS_Components.md), [ECS_Systems.md](ECS_Systems.md)
(generated by `systems/ecs/tools/gen_docs.py`).

**Addresses:** `RVA = runtime - 0x140000000`, `Ghidra = 0x7ff64ffe0000 + RVA`. Function
names below are Ghidra `FUN_` addresses unless noted otherwise.

**Status legend:** [G] read in Ghidra, [L] verified live via Prometheus, [?] inferred, not yet verified.

Live snapshots: `systems/ecs/manifest/ecs_{game,session,lobby}.json`, produced by the Prometheus
MCP tool `ecs_dump` (ea = `game` | `session` | `lobby` | `0x<addr>`).

## 1. Entity admins

Three EAs exist from the title screen onwards and each ticks once per render frame [L]:

| EA | how to find | vtable RVA | systems | notes |
|---|---|---|---|---|
| game | global `0x17b7f90` (Prometheus `GameEntityAdmin()`) | `0x15c37b0` | 50 (+1 Prometheus) | built in `FUN_7ff650bde670` (startup) |
| session | `*(global 0x17b7fc0) + 0xB8` | `0x15c37b0` | 40 | subset of game EA systems + `0x15d2f18` |
| lobby | global `0x1833e18` | `0x15c3430` | 21 | entirely different system set |

### EntityAdmin fields (behaviourally relevant)

| +0x48/+0x50 | **delete-request queue** (entities) |

| +0x68 | spinlock for the destroy queues |

## 2. Entities

| off | meaning |
|---|---|
| +0x00/+0x08/+0x10 | parent / first child / next sibling |
| +0x18 | UUID (16 B, from loader) |
| +0x28 | owning EA |
| +0x30/+0x38 | resource load entries |
| +0x50/+0x58 | component list `teList<Component*>`, **sorted by component id, null-terminated** (hence `num - 1`) |
| +0x90 | global entity id (released to a global list on destroy, then `-1`) |
| +0x94 | entity id (EA-local) |
| +0x98..+0xAF | 192-bit component mask |
| +0xB0..+0xB2 | prefix popcounts of the mask words 0,1,2 (rank index) |
| +0xB4 | lifecycle flags (below) |

**O(1) component lookup** [G, `FUN_7ff650809b00`]: `index = prefix[id>>6] + popcount(mask[id>>6] & ((1<<(id&63))-1))`
into the sorted component list. This is why the list stays sorted and why component ids are < 192.

**Flags (+0xB4)** [G]: `0x1` components created, `0x2` in pending-created queue, `0x4` delete requested,
`0x8` delete requested with "immediate" arg, `0x10` in pending-destroy queue, `0x20` (skip delete, with 0x10 set),
`0x40` loader gave it an explicit tag (`+0xB8`), `0x80` external storage (not pool), `0x100` custom deallocator.

## 3. Systems

`systems_array` holds instances; vtable at +0, EA backref at +8 [L].

| slot | off | meaning | when |
|---|---|---|---|
| 0-2 | 0x00 | inheritance (get type / is_assignable / is_instance_of) | `InsertSystemBefore` uses slot 2 |
| 3 | 0x18 | name, **stripped**: shared fn returns `""` [L] | |
| 4 | 0x20 | deleting destructor | |
| 5 | 0x28 | `OnInitialize() -> bool` | EA init; any false = init fails |
| 7 | 0x38 | `PreDelete()` | EA shutdown |
| 8 | 0x40 | `GetSubscriptions(int* count) -> u8*` | EA init; default `0x5a45e0` returns null |
| 9 | 0x48 | `OnEntityAdded(Entity*)` | pending-created flush |
| 10 | 0x50 | `OnEntityCreated(Entity*)` | immediately at spawn |
| 11 | 0x58 | `OnEntityDeleting(Entity*)` | immediately at delete request |
| 12 | 0x60 | `OnEntityRemoved(Entity*)` | real destroy |
| 13 | 0x68 | `OnTick(float dt)` | every EA tick; default `0x5a0c20` is a no-op |

**Registration** [G]: `FUN_7ff6507ef3f0` = `AppendSystem(ea, sys)`; `FUN_7ff6507ef450` =
`InsertSystemBefore(ea, sys, type)`, which inserts before the first system with `is_instance_of(type)`
and **silently drops the system if none matches**. Both set `sys+8 = ea`. Tick order is therefore
exactly the explicit construction order.

**Subscriptions** [G `FUN_7ff6507ef200`, L]: at EA init every system is appended to `EA+0xB8[id]` for
each id it returns, with **no de-duplication**. Index 0 (global byte `0x189229f`) is the "every entity"
list, empty in all three EAs [L].

**Matching an entity to systems** [G `FUN_7ff6507ef680`]: collect `EA+0xB8[0]` then `EA+0xB8[id]` for
each of the entity's components in ascending id. A system subscribed to *n* of an entity's components is
therefore called **n times** for that entity [G; verify with a trace]. Example: system `0x15c1ac8`
subscribes to `0x09,0x15,0x0a`.

## 4. Components

Runtime ids come from two places: entity definitions list STU component types, converted by
`FUN_7ff650ec7d70` (STU type hash → id; a few hashes map to nothing, e.g. `STUMirroredEntityComponent`,
`STUAreaComponent`, `STUUXComponent`), and engine code (dependencies, specialised loaders such as the
player-controller loader `FUN_7ff650ce74c0` adding `0x13, 0x2f, 0x33, 0x3f`). Component and creator names are
stripped (every creator is named "Unknown").

- Created by `EA+0x38[id]->vf[1]()`, then `comp+0x10 = id`, `comp+8 = entity`, appended to the entity list, mask bit set [G `FUN_7ff650809a30`].
- **Dependencies** [G `FUN_7ff6507ef8d0`, L]: after all loader-requested components exist, each one's dependency list (creation info) is walked depth-first and missing components are added. The full graph is in the manifest (`components[].dependencies`).
- Component vtable [G]: `+0x10 OnCreate(loader)`, `+0x20` post-create (after flag 1), `+0x28 CanDelete() -> bool`.
- Per-type iteration lists `EA+0xB0[id]` are sorted by component pointer. Components enter them at the created flush and leave them at destroy, unless a global per-type table (`0x1828ec8`, stride 0x20) marks the type as untracked [G].
- Systems iterate a type with `FUN_7ff6509b79f0` / `FUN_7ff6509b80b0` (begin/next over `EA+0xB0 + id*0x18`) [G].

## 5. Lifecycle

### Spawn [G `FUN_7ff6507ef7c0`, under the EA lock]
1. **Allocate** (`FUN_7ff6507efd90`): if the requested id is default (or its low 29 bits are all 1), `id = loader->vf[0x50]() | ++EA[+0xC0]` (high bits from the loader). If an explicit id **already exists, spawn fails (returns null)**. Take an entity from the pool, set EA/id, insert into the id hash, UUID from the loader.
2. **Children**: for each child loader, spawn recursively and **prepend** to the parent's child list.
3. **Finalize** (`FUN_7ff6507ef9d0`):
   1. add loader components, then add missing dependencies
   2. sort the component list by id, append the null terminator
   3. `loader->vf[0x40](ent)`
   4. `comp->OnCreate(loader)` for each component, ascending id
   5. flag `|= 1`
   6. `comp->vf[0x20]()` for each component
   7. `loader->vf[0x48](ent)`
   8. **`OnEntityCreated`** for each matched system
   9. flag `|= 2`, push to the pending-created queue

### Inline (lightweight) entities [G `FUN_7ff6507f0030`, L]
`SpawnInline(ea, u8* comps, count, loader)`: the entity and all components live in **one allocation**.
- Per-type global table at RVA `0x1828eb0`, stride 0x20: `+0x00` in-place constructor `(mem, loader, entity)`, `+0x08` entity allocator (optional), `+0x10` handler (custom deallocator), `+0x18` inline size. Size ≠ 0 ⇒ inline-capable: `0x01` (544 B), `0x03` (1616), `0x04` (528), `0x05` (64), `0x0b` (48), `0x0d` (224). The flushes skip exactly these types for the iteration lists.
- Flags `0x80`, or `0x180` if the **last** component type has an entity allocator (all map shapes seen: `0x181`).
- `id = ++counter | 0x80000000` (atomic, before taking the EA lock), insert into the id hash under the lock, `loader->vf[0x40](ent)` **before** the components exist, construct components in the given order (no sort, **no dependencies**), flag 1, `vf[0x20]` post-create. **No system callbacks, no created queue, no iteration lists.**
- Factories: `FUN_7ff6509d3280` = `{0x01,0x05}`, `FUN_7ff6509d33f0` = `{0x01,0x03,0x0d}`; `{0x01,0x03,0x0b}` also seen. During the Anubis load the game EA got 688 of these (map geometry/scene objects); destroy skips `on_removed` (flag 0x80).

### Pending-created flush [G `FUN_7ff6507f0600`]
For each queued entity: clear flag 2, **`OnEntityAdded`** for each matched system, insert components into the iteration lists (reverse order). Then clear the queue.

### Delete request [G `FUN_7ff6507eff50` → `FUN_7ff6507f03f0`]
1. Unlink from parent, then delete children recursively (always the current first child).
2. If flags & 0x30 are already set, return. Otherwise flag `|= 4` (or `0xC`), then **`OnEntityDeleting`** for each matched system.
3. Ask each component, in reverse order, `CanDelete()`. Only if **all** return true: flag `|= 0x10`, push to the pending-destroy queue. [?] Who retries otherwise is unknown.

### Destroy [G `FUN_7ff6507f0880`]
Remove from the pending-created queue if still there, then **`OnEntityRemoved`** for each matched system, remove components from the iteration lists, destroy components (`FUN_7ff650809d00`), release the global id, release resource entries, remove from the id hash, and return the entity to the pool.

## 6. Tick

`EntityAdmin::Tick(ea, dt)` = `FUN_7ff6507f15d0` [G]:
1. `++tick_count` (+0xC8)
2. EA `vf[0x40]` (pre-tick hook)
3. **Destroy flush** (`FUN_7ff6507f0d30`): global callbacks (`0x1893e20`); drain the delete-request queue (`+0x48`) through the delete-request path; drain the pending-destroy queue (`+0x70`) through Destroy. Each drain loops until its queue is empty.
4. **Created flush** (`FUN_7ff6507f0600`)
5. global pre-tick callbacks (`0x1893df0`, count `0x1893df8`)
6. for each system in order: EA `vf[0x48](sys)`, **`sys->OnTick(dt)`**, EA `vf[0x50](sys)`
7. global post-tick callbacks (`0x1893e08`, count `0x1893e10`)
8. EA `vf[0x58]` (post-tick hook)

Consequence: an entity spawned during system N's tick has had `OnEntityCreated` already, but only
appears in iteration lists and gets `OnEntityAdded` at the start of the **next** tick. Deletions
requested during a tick are processed at the start of the next tick.

### Frame loop [G `FUN_7ff650bdf460`]
Per render frame: the session driver `FUN_7ff650c602a0` ticks the session EA (dt from the clock
`FUN_7ff650be3be0` → `FUN_7ff650d2cc90`, plus up to 20 catch-up ticks while an accumulator is behind),
then the game EA (clock dt), then the lobby EA (constant dt `0x179f0e0`), then the frame limiter sleeps.

**EA ticks run at render rate.** Fixed 16 ms command frames are handled inside systems. For example,
`FUN_7ff650c0fd80` walks the Statescript components (`EA+0xB0[0x23]`) and gives each a budget of
`CF count × 16000 µs` (`FUN_7ff650ce84a0`), deferring those over the time budget. Netcode clock
details: memory note "netcode-clock-findings" (its addresses are Ghidra − `0x7ff650000000`, i.e. RVA − `0x20000`).

## 7. Trace findings (live, 2026-09-25)

Recorded with the Prometheus MCP `ecs_trace` tool (`systems/ecs/tools/live.py trace ...`). Fixtures:
`systems/ecs/fixtures/trace_mapload_anubis.json` (title screen → `!instance` → Temple of Anubis loaded) and
`trace_setup_controller.json` (game server `/setup`: local controller + 23 networked entities).

- **Duplicate callbacks confirmed** [L]: game system 9 (subs `0x2d,0x29,0x64`) got `on_created` *and* `on_added` twice for each of 302 entities carrying two of those components. Reproduce this, don't "fix" it.
- **Callback order** [L]: per entity, subscriber lists in ascending component id, and within one list in system registration order. For controller `0x40000001`: `0x0e`→22, 43; `0x13`→49; `0x20`→13; `0x2f`→29.
- **Systems flush mid-tick** [L]: game system 8 (vtable `0x15c28c8`, the replication/mirror system) spawns all networked entities during its `OnTick`, then calls `FlushCreated` itself in the same tick. `on_added` does not always wait for the next tick.
- **Who spawns during map load** [L]: systems 36 and 43 (1008 spawns each, game and session EA in parallel), a few from 16, 6, 1. The session EA gets its own copy of the map entities.
- **Entity ids** [L]: client-created `0x8000xxxx` (counter + loader high bits), server-replicated `0x4000xxxx` (explicit id from the server).
- **Deletions during load** [L]: 393 requests / 107 destroys (game EA). Flags after the request are `0x185` (requested, a component refused `CanDelete`) or `0x195` (queued). All have `0x80` (external storage), which skips `on_removed`; no subscriber matched, so no `on_deleting` either.
- **More EAs** [L]: two additional EAs (`0x38f3f40`, `0x3ed9cb0`) only delete entities during load; not yet identified.
- The session EA is recreated on map load (new address).
- **Threads** [L]: map-loader threads create inline entities *concurrently* with the main thread's systems (and with each other); the atomic id counter makes the id order racy. Everything else ran on the main thread.
- **Cross-EA work** [L]: a system of one EA spawns/deletes in another (game systems 24 and 38 create lobby inline entities; 872 events of another EA ran inside game-EA phases).
- **Components drive deletions** [L]: a component asked `CanDelete` may request the deletion of *another* entity (an owned helper): nested `delete_request` of a non-child. Destroying an inline entity runs component destructors that ask to delete their own entity again (no-op, flag 0x10 set). Deletes often need several requests (`CanDelete` refuses for a few ticks: flags stay `0x185`).
- **No reparenting** [L]: with `ecs_trace watch_parents=true` (every entity's parent compared around every system OnTick, all EAs) a full map load + `/setup` shows zero parent changes; the parented entities (43 game, 31 session) are exactly the loader children. Parents come only from `Spawn` children. (A nested delete of a non-child is a component's `CanDelete` side effect, not a parent link.)
- **Component destruction order** [G `FUN_7ff650809d00`]: reverse list order (highest id first). Pool entities: `creator->vf[0x10](creator, comp)` (destructor if creator flag 0x10, then the allocator's free); inline entities: `comp->vf[0x18]()` then the destructor in place.
- **Iteration order** [G, L]: per-type lists are sorted by component address, which the per-type page allocator decides (vtable `0x157f0f0`; alloc `FUN_7ff6507f31f0`, free `FUN_7ff6507f3350`). Pages of **256 slots** (allocator +0x40), slot stride at +0x54; a page hands out **fresh slots top-down** (bump pointer, descending addresses) and only then its **LIFO free list**; allocation starts at the current page and checks up to 16 pages; freeing makes a page with fewer used slots current, an empty page is released. So a type iterates newest-first within a page. Verified: the library's allocator model reproduces the client's order for all 19 (game) / 17 (session) types created during the map load, including the 2 where freed slots were reused. [?] Order *between* pages depends on OS page addresses (assumed: newer page = higher).

### Replay status
`systems/ecs/tests/replay_fixture.py` rebuilds the client's *actions* from a trace (who spawned what in which tick/system, loader component lists recovered from the add order + dependency table, child trees, inline spawns, explicit flushes, delete requests with the client's `CanDelete` answers, parent links, racy id counters, external/cross-EA work) and checks that the library produces the identical *consequences*. **All fixtures match exactly** (setup 384 events; map load game 10460, session 8449, lobby 71; command
frames 7315 clock/listener events per EA; the map-load replay drives the clock with the recorded dt and
resyncs), and the per-type iteration order after the map load matches the client's dump (`fixtures/dump_mapload_{start,end}_*.json`).

## 8. Architecture from the component/system catalogue

From mapping all 71 systems and 118 component types ([ECS_Systems.md](ECS_Systems.md),
[ECS_Components.md](ECS_Components.md); per-entry confidence there).

**Two rates.** `OnTick` runs once per render frame. Fixed 16 ms **command frames** are driven by
`CommandFrameSystem` (game #16, `0x15c1b48`) [G, verified `FUN_7ff650fef420`]: it pulls the pending CF list
from the EA clock (`EA+0x218`, +0x50), and per CF writes singleton **`0x4d` CommandFrameClock**
(+0x18 CF, +0x20 CF×16 ms, +0x28 phase) and calls every **CF listener** in `EA+0xF0`/`+0xF8`:
slot 0 `OnCommandFrame(cf, flags 1=first|2=last)`, +8 pre, +0x10 post. Afterwards entries of the deferred
per-CF queue `EA+0x110` older than the CF are dropped. Singleton `0x6b` holds the last server-confirmed CF
(live: 33 CF behind `0x4d`, the ~35 CF lead from the netcode notes). Simulation that must match the server
(movement, projectiles every 16000 µs, weapons, unsynchronized movers) lives in CF listeners.

Full write-up of timing, dilation and the server's role: [CommandFrames.md](CommandFrames.md).

**Clock** [G, L: formulas verified on every tick of `fixtures/trace_command_frames.json`]. Timing object
`EA+0x218`; the netcode clock is at timing+0x50. `GameClockSystem` (game #1 / session #0, `FUN_7ff650c7d4b0`)
stores dt (+0x20), accumulates seconds (+0x28) and render frames (+0x38), then:
1. `FUN_7ff650ce63a0` dilation: `µs = (int64)(dt * 1e6f)`; flags at clock+0xa8: bit 0 → −200 µs (−1000 with
   bit 3), else bit 1 → +200 µs (+1000 with bit 3); also smooths the lead values at clock+0x80/+0x84.
2. `FUN_7ff65100e950` advance: clear the pending list (+0x20/+0x28) and +0x08; `step = clamp(µs, 0, 250000)`;
   `acc(+0x00) += step`; while `acc >= 16000`: `acc -= 16000`, `+0x08 += 16000`, `++cf (+0x10)`, append cf.

**CommandFrameSystem tick** [G `FUN_7ff650c167d0`, L]: every listener's slot 1 (pre, also when no CF is due);
`0x4d`+0x28 = 1; if CFs are pending, `FUN_7ff650feea30(first, last)`: EA vfunc 0x70 → vfunc 0x20 object
gets +0x18 = 1 (simulating), then per CF: `0x4d` {+0x18 cf, +0x20 cf·16000/1000}, flags 1 = first, 2 = last,
`FUN_7ff650fef420(cf, flags)` (all listeners' slot 0 in list order, then prune `EA+0x110`); afterwards
`FUN_7ff65101fc30` and the flag is cleared; `0x4d`+0x28 = 2; every listener's slot 2 (post).

**Listeners** [G EA builder `FUN_7ff650be0fd0`, L]: registered after all systems are built, in this order
(game and session): #17 PhysicsAreaRegistry (+0x38), #18 CollisionProxySync (+0x10), #19 UnsynchronizedMover
(+0x10), #20 LocalPlayerMovementReconcile (+0x10), #21 WeaponAttachment (+0x10), #22 StatescriptSystem (+0x38),
#23 ProjectileNetworkReceive (+0x398). The lobby EA has none. Listeners do real work: e.g. the Statescript
listener spawns effect entities inside `OnCommandFrame` (the tracer attributes such work to phase
`cf_listener` with the listener index and CF).

**Library**: `include/ecs/command_frame.h` (clock, listener interface, `0x4d` component, deferred queue),
`command_frame_systems.h` (`GameClockSystem`, `CommandFrameSystem`); `manifest::AddSystems` uses them at the
client's indexes and registers stand-in listeners in the client's order. The CF fixture replays exactly
(8128 clock/listener events per EA), and the map-load replay now drives the clock with the recorded dt.

**Systems with a second interface.** Several systems override no slots at all (e.g. game #19, #21, #18, #23,
#50) and do their work through a subobject at `sys+0x10` with its own vtable, registered on one of the EA's
listener lists (CF listeners `EA+0xF0`, map-load listeners `EA+0x180`, network channel handlers).
"No overridden slots" ≠ idle.

**Map-load listeners** `EA+0x180`: slots +8…+0x30 are the load phases in order (`MapLoadSystem` #6 drives
them; +0x30 load complete), +0x38 unload.

**Singleton components.** Many component types exist exactly once per EA on an engine-made entity
(`0x80000001` in each EA) and serve as system-owned state accessed via "first item of `EA+0xB0+id*0x18`":
e.g. `0x4d` CommandFrameClock, `0x55` GameSceneWorld, `0x57` EffectPhysicsWorld, `0x64` PathdataRebuildQueue,
`0x70` ProjectileNetBuffer, `0x72` EntityAABBTree; in the lobby EA `0x50` Input/Options, `0x5f` Chat,
`0x60` Party, `0x56` Matchmaking, `0x65` PlayerNameCache.

**Other EA services**: `EA+0x198` component-field-change callback registry (vfunc 0x10 = register(callback,
componentId, ctx); used e.g. by the lobby to watch game-EA `0x35`); `EA+0x1d0` network send interface
(JAM to the server); EA vfunc `0x70` network/session object; lobby EA vfunc `0xe0` UI manager.

**Network path (client)**: `NetworkEventSystem` #3 (UDP transport tick, connect events, per-channel
dispatch) → `JamSystem` #4 (connection health, heartbeat) → `MirrorSystem` #8 (replication receive: create /
update / destroy records, spawns `0x4000xxxx` entities, flushes created) and channel handlers (projectiles
#23, replay #46, instance JAM router #44) → … → `NetworkSendSystem` #45 (one packet per 16 ms from
registered writers). Client-predicted entities (`0x6xxxxxxx`) come from `PredictedEntitySpawnSystem` #50 and
are deleted unless confirmed within 6 frames.

**Anti-tamper noise**: many system functions contain rdtsc / GetTickCount64 / random code-page CRC blocks
(constant `0xffffffb9…`, `DAT_7ff6517fd478`); they are not system logic.
